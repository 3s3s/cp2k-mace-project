# Руководство по развертыванию и запуску Master–Worker архитектуры (DFT / CP2K)

Данный документ содержит пошаговые инструкции по запуску веб-панели управления, сервера-мастера (`main.py`) и воркеров (`worker.py`) в Docker-контейнерах для различных сценариев окружения.

---

## 🛠 Предварительные требования

1. **Файл `main.py` (Master).**

   Убедитесь, что в вызове `uvicorn.run` указан хост `0.0.0.0` (а не `127.0.0.1`), чтобы сервер мог принимать соединения из внешних Docker-сетей или по интернету:

   ```python
   def run_fastapi_server(port: int):
       uvicorn.run(app, host="0.0.0.0", port=port, log_level="warning")
   ```

2. **Зависимости контейнера.**

   Убедитесь, что в Docker-образ установлен пакет `requests`:

   ```bash
   pip3 install requests
   ```

---

## 🌐 Веб-интерфейс управления `main.py`

Веб-сервер на Node.js (`./src/webserver/index.js`) поднимает HTTPS-панель на порту `8443` (пробрасывается через `--port` в `run.sh`). Через браузер можно редактировать `config.json`, запускать и останавливать `main.py`, следить за логом и состоянием очереди/воркеров.

### Интерактивный запуск веб-панели (из корня проекта)

Подходит для отладки, пока открыт терминал:

```bash
npm start
```

*(Останавливается нажатием `Ctrl+C`.)*

### Фоновый запуск веб-панели через `forever`

Чтобы веб-сервер работал в фоне и не останавливался при закрытии терминала внутри контейнера:

```bash
npm install -g forever
forever -s start ./src/webserver/index.js
```

Полезные команды `forever`:

```bash
forever list                              # список запущенных процессов
forever logs                              # посмотреть пути к логам forever
forever stop ./src/webserver/index.js    # остановить веб-сервер
forever stopall                            # остановить все процессы forever
```

После запуска веб-панели откройте в браузере `https://<хост>:<порт_8443>` (например, `https://127.0.0.1:8443`) и нажмите **«Запустить main.py»**, указав нужный порт FastAPI-очереди (по умолчанию `8000`).

## 💻 Сценарий 1: Все компоненты на одной машине (локально в Docker)

Этот сценарий используется для отладки, когда Master и Worker работают на вашем локальном компьютере (или в WSL2), но запущены в **разных** Docker-контейнерах.

### 1.1 Запуск Мастера (Master) и веб-панели

```bash
# Запускаем контейнер для Мастера (8443 -> веб-панель, 8000 -> очередь FastAPI)
./run.sh --cpu --name master --port 8443 --port2 8000
```

Внутри контейнера можно запустить `main.py` вручную:

```bash
python3 ./src/main.py --port 8000
```

Либо поднять веб-панель (`npm start` или `forever -s start ./src/webserver/index.js`) и запустить `main.py` кнопкой в интерфейсе браузера.

### 1.2 Запуск Воркера (Worker)

В **другом терминале** запустите воркер. Скрипт `run.sh` автоматически свяжет воркер с сервером через `host.docker.internal`.

**Вариант А. Автоматический запуск воркера при старте контейнера:**

```bash
./run.sh --cpu --name worker1 --port 8444 --port2 8001 --worker
```

**Вариант Б. Ручной запуск из bash-оболочки контейнера:**

```bash
# Запуск контейнера
./run.sh --cpu --name worker1 --port 8444 --port2 8001

# Внутри контейнера (переменные MASTER_HOST и MASTER_PORT подтягиваются автоматически)
python3 ./src/worker.py
```

## 🌐 Сценарий 2: Распределенный запуск (Master на удаленном сервере с реальным IP)

Этот сценарий используется для расчетов, когда `main.py` запущен на удаленном сервере (например, IP `203.0.113.10`), а воркеры запускаются на других машинах или в отдельных контейнерах.

### 2.1 Настройка и запуск на удаленном сервере (Master)

1. Откройте порт `8000` (и при необходимости `8443` для доступа к веб-панели из браузера) во входных правилах брандмауэра (UFW / Cloud Security Group):

   ```bash
   sudo ufw allow 8000/tcp
   sudo ufw allow 8443/tcp
   ```

2. Запустите контейнер Мастера на удаленном сервере:

   ```bash
   ./run.sh --cpu --name master --port 8443 --port2 8000
   ```

3. Внутри контейнера запустите веб-панель (`forever -s start ./src/webserver/index.js` или `npm start`) и стартуйте `main.py` через интерфейс либо напрямую командой:

   ```bash
   python3 ./src/main.py --port 8000
   ```

### 2.2 Варианты подключения Воркера к удаленному серверу

#### Способ 1: Прямое подключение по публичному IP

Используйте флаг `--master-host` для указания реального IP-адреса сервера:

```bash
./run.sh --cpu --name worker1 --port 8444 --port2 8001 --master-host 203.0.113.10 --worker
```

Или, если контейнер воркера уже запущен, вызовите скрипт напрямую с параметром `--server`:

```bash
python3 ./src/worker.py --server 203.0.113.10 --port 8000
```

#### Способ 2: Подключение через SSH-туннель

Если порт `8000` закрыт снаружи на удаленном сервере:

1. **На машине с Воркером** откройте SSH-туннель в отдельном терминале:

   ```bash
   ssh -N -L 8000:127.0.0.1:8000 user@203.0.113.10
   ```

2. **Запустите воркер** как при локальной работе:

   ```bash
   ./run.sh --cpu --name worker1 --port 8444 --port2 8001 --worker
   ```

## 🔄 Фоновый запуск воркеров и их остановка

Чтобы воркер продолжал работать после закрытия терминала или отключения SSH-сессии, есть два удобных способа.

### Способ А: Контейнер в фоне (`-d` / `--detach`) + автоматический старт воркера (`--worker`)

`run.sh` поддерживает фоновый режим `-d` (`--detach`) и флаг `--worker`:

```bash
./run.sh -d --cpu --name worker1 --port 8444 --port2 8001 --worker
```

*(При необходимости добавьте `--master-host 203.0.113.10`.)*

Как управлять таким воркером:

```bash
docker ps                                  # проверить статус контейнера
docker logs -f cp2k-mace-cpu-worker1       # смотреть живой вывод воркера
docker stop cp2k-mace-cpu-worker1          # штатно остановить контейнер и воркер
docker rm -f cp2k-mace-cpu-worker1         # принудительно остановить и удалить контейнер
```

### Способ Б: Запуск `worker.py` в фоне внутри уже запущенного контейнера (`nohup`)

Если контейнер уже запущен в интерактивном режиме и вы хотите отвязать процесс `worker.py` от текущей оболочки перед выходом из терминала:

```bash
nohup python3 ./src/worker.py > /workspace/results/worker_nohup.log 2>&1 &
```

Персональный лог каждого воркера при этом всё равно пишется в `results/worker_logs/worker_N.log`.

Как найти и остановить такой фоновый `worker.py`:

```bash
ps aux | grep worker.py                    # найти PID процесса worker.py
kill <PID>                                 # мягкая остановка
kill -9 <PID>                              # принудительная остановка, если процесс завис
```

## 🚀 Запуск нескольких воркеров параллельно

На одной машине можно запустить несколько фоновых воркеров с разными именами контейнеров и портами:

```bash
./run.sh -d --cpu --name worker1 --port 8444 --port2 8001 --worker
./run.sh -d --cpu --name worker2 --port 8445 --port2 8002 --worker
./run.sh -d --cpu --name worker3 --port 8446 --port2 8003 --worker
```

Каждый воркер получит свой `worker_id` (`worker_1`, `worker_2`, `worker_3`) и начнет забирать задачи из очереди `main.py`.

---

## 🔍 Проверка логов и диагностика

- **Логи Мастера (`main.py`):** файл `results/main.log` (также отображается в веб-интерфейсе).
- **Логи Воркеров:** персональные файлы `results/worker_logs/worker_N.log`.
- **Устойчивость к обрывам связи:** воркер автоматически повторяет попытки подключения к серверу при недоступности Мастера или сетевых сбоях без падения процесса.
